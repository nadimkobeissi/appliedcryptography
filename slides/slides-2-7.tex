\section{Bitcoin}

\begin{frame}{The problem: trust in digital commerce}
	\begin{itemize}
		\item Online commerce relies on financial institutions as trusted third parties: banks, payment processors, and credit card companies mediate every transaction.
		\item The Bitcoin whitepaper\footnote{\url{https://bitcoin.org/bitcoin.pdf}} opens by listing what this costs us:
		      \begin{itemize}
			      \item \textbf{High transaction costs}: mediation makes micropayments impractical.
			      \item \textbf{Reversibility spreads distrust}: merchants demand ever more customer information.
			      \item \textbf{Fraud is priced in}: some percentage of fraud is simply accepted as a cost of doing business.
			      \item \textbf{No digital cash}: physical cash works person-to-person; nothing digital does.
		      \end{itemize}
		\item Its proposal: replace trust with cryptographic proof.
	\end{itemize}
\end{frame}

\begin{frame}{Peer-to-peer electronic cash}
	\begin{itemize}
		\item Replace trust with cryptographic proof.
		\item Enable direct transactions between parties without intermediaries.
		\item Key properties needed:
		      \begin{itemize}
			      \item Computationally impractical to reverse (protects sellers).
			      \item Optional escrow mechanisms (protects buyers).
			      \item No reliance on third parties.
		      \end{itemize}
	\end{itemize}
\end{frame}

\begin{frame}{Core challenge: double-spending}
	\begin{itemize}
		\item Digital information can be copied perfectly.
		\item Without a central authority, how do we prevent spending the same coin twice?
		\item Traditional solution: Central mint/bank tracks all transactions.
		\item Problem: This reintroduces the trusted third party.
	\end{itemize}
\end{frame}

\begin{frame}{Bitcoin's solution in one slide}
	\begin{itemize}
		\item A peer-to-peer network acts as a \textbf{distributed timestamp server}: it agrees on the order of transactions without anyone being in charge.
		\item The ordering is backed by \textbf{computational proof}: rewriting history means redoing the computation.
		\item Security assumption: honest nodes control a majority of the CPU power.
		\item The ingredients are almost all things we already know:
		      \begin{itemize}
			      \item Digital signatures (1.7, 1.8) prove who may spend a coin.
			      \item Hash functions (1.6) chain blocks together and power the proof-of-work puzzle.
			      \item Merkle trees (2.6) let a phone verify a payment without the whole ledger.
			      \item Plus something new for this course: \textbf{economic incentives} for honest behavior.
		      \end{itemize}
		\item The rest of this section unpacks each piece.
	\end{itemize}
\end{frame}

\begin{frame}{Historical context}
	\begin{itemize}
		\item Published October 31, 2008 by ``Satoshi Nakamoto'', a pseudonym; the network went live in January 2009.
		\item Nobody knows who Nakamoto is. The paper and the software are all we have.
		\item Almost every ingredient already existed:
		      \begin{itemize}
			      \item Digital signatures on elliptic curves (ECDSA).
			      \item Hashcash proof-of-work (Adam Back, 1997).
			      \item Hash-chained timestamps (Haber \& Stornetta, 1991).
			      \item b-money (Wei Dai, 1998) and bit gold (Nick Szabo, 2005): decentralized money proposals that never shipped.
		      \end{itemize}
		\item The new part was the combination: using proof-of-work to decide who appends to the ledger.
	\end{itemize}
\end{frame}

\begin{frame}{The Byzantine Generals Problem}
	\begin{itemize}
		\item Classical problem in distributed computing (Lamport, Shostak, Pease, 1982).
		\item Scenario: several generals surround a city and must agree on a common plan (attack or retreat).
		      \begin{itemize}
			      \item They can only communicate via messengers.
			      \item Some generals are traitors who send inconsistent messages to different colleagues.
			      \item Goal: all loyal generals decide on the same plan, whatever the traitors do.
		      \end{itemize}
		\item Lamport et al.\ show it is solvable when the participants are known: with unforgeable signatures, any number of traitors can be tolerated; without them, fewer than a third.
		\item \textbf{Bitcoin's setting is harder}: anyone can join or leave, nobody knows how many participants there are, and one attacker can pretend to be a thousand.
		\item This is the problem proof-of-work addresses. Let's build up to it.
	\end{itemize}
\end{frame}

\subsection{Blockchains}

\begin{frame}{Let's start with the basics: what's a blockchain?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Think of it like a notebook:}
			\begin{itemize}
				\item Pages = blocks
				\item Each page lists transactions
				\item Pages linked together in order
				\item Can't tear out or reorder pages
			\end{itemize}
			\textbf{But it's distributed:}
			\begin{itemize}
				\item Everyone has a copy
				\item No single owner
				\item Need agreement to add pages
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The cryptographic glue:}
			\begin{itemize}
				\item Each block contains:
				      \begin{itemize}
					      \item List of transactions
					      \item Hash of previous block
					      \item Timestamp
					      \item Special ``proof'' (we'll see why!)
				      \end{itemize}
			\end{itemize}
			\begin{alertblock}{Key insight}
				The hash links make history tamper-evident: change one block and every hash after it breaks. Making tampering \emph{expensive} is the next step.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The challenge: who gets to add the next block?}
	\begin{center}
		\textbf{In a decentralized system with no leader, how do we decide?}
	\end{center}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Can't use traditional voting:}
			\begin{itemize}
				\item One-person-one-vote?
				      \begin{itemize}
					      \item How to verify identities?
					      \item Attacker creates 1000 fake identities
					      \item This is a ``Sybil attack''
				      \end{itemize}
				\item Central authority decides?
				      \begin{itemize}
					      \item Defeats the whole point!
					      \item Back to trusting intermediaries
				      \end{itemize}
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Bitcoin's answer:}
			\begin{itemize}
				\item Make it expensive to add blocks
				\item But anyone can try!
				\item Winners prove they did work
				\item Can't fake the work
			\end{itemize}
			\begin{exampleblock}{This is Proof-of-Work}
				Replace ``one identity = one vote'' with ``one CPU = one vote''
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\subsection{Proof-of-Work}

\begin{frame}{Proof-of-work: a puzzle anyone can solve (but slowly)}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The basic idea:}
			\begin{itemize}
				\item To add a block, solve a puzzle
				\item The puzzle is expensive to solve
				\item But cheap to verify
				\item Like Sudoku: hard to fill in, trivial to check
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{What we need from the puzzle:}
			\begin{itemize}
				\item \textbf{Cheap to verify}: everyone checks every block
				\item \textbf{Progress-free}: no shortcuts, nothing to precompute
				\item \textbf{Tunable}: harder or easier on demand
				\item \textbf{Tied to the block}: one solution, one block
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{alertblock}{Key property}
		You prove you spent real resources; anyone can verify cheaply. A thousand fake identities buy nothing: the work is the same.
	\end{alertblock}
\end{frame}

\begin{frame}{The hash lottery: Bitcoin's specific puzzle}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The puzzle:}
			\begin{itemize}
				\item Take your block data
				\item Add a random number (nonce)
				\item Hash everything: $H =$ SHA-256(SHA-256(block $\|$ nonce))
				\item Check if $H$ starts with many zeros
				\item If not, try different nonce
				\item Repeat until you find one!
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Example hashes:}
			\begin{itemize}
				\item \texttt{00000000000000000007b...}
				      \begin{itemize}
					      \item Winner! (19 leading zeros)
				      \end{itemize}
				\item \texttt{5fec4ba9f3c2d8a1b9e7...}
				      \begin{itemize}
					      \item No good, try again
				      \end{itemize}
			\end{itemize}
			\begin{exampleblock}{Why hashing?}
				Each attempt is independent -- you can't get ``closer'' to a solution, only keep trying
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{How hard is this puzzle really?}
	\begin{center}
		\textbf{Let's look at real Bitcoin numbers}
	\end{center}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Difficulty in 2024:}
			\begin{itemize}
				\item Need $\approx$19--20 leading hex zeros
				\item That's $\approx$76--80 leading zero bits
				\item Finding a hash smaller than $\approx 2^{180}$ out of $2^{256}$ possible
				\item Probability per attempt: $\approx \frac{1}{2^{76}}$, astronomically small!
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{In practice (2024):}
			\begin{itemize}
				\item Network tries $\approx 600 \times 10^{18}$ hashes per second
				\item That's 600 exahashes/second!
				\item All to find one valid block
				\item Every 10 minutes on average
			\end{itemize}
			\begin{alertblock}{Mind-boggling scale}
				More computations than there are grains of sand on Earth, every 10 minutes!
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The difficulty adjustment: Bitcoin's thermostat}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The problem:}
			\begin{itemize}
				\item More miners join $\rightarrow$ blocks too fast
				\item Miners leave $\rightarrow$ blocks too slow
				\item Want consistent 10-minute blocks
			\end{itemize}
			\textbf{The solution:}
			\begin{itemize}
				\item Every 2016 blocks ($\approx$2 weeks)
				\item Measure actual time taken
				\item Adjust difficulty up or down
				\item Like a thermostat!
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{How adjustment works:}
			\begin{itemize}
				\item Blocks coming too fast?
				      \begin{itemize}
					      \item Require more leading zeros
					      \item Makes puzzle harder
				      \end{itemize}
				\item Blocks coming too slow?
				      \begin{itemize}
					      \item Require fewer leading zeros
					      \item Makes puzzle easier
				      \end{itemize}
			\end{itemize}
			\begin{alertblock}{Result}
				Stable 10-minute block time since 2009, despite hashpower growing by more than ten orders of magnitude!
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Difficulty adjustment: the technical details}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{What Bitcoin measures:}
			\begin{itemize}
				\item Every 2016 blocks
				\item Calculate actual time taken
				\item Target: 20,160 minutes (2 weeks)
				\item Compare actual vs. target
			\end{itemize}
			\textbf{The adjustment formula:}\footnote{\url{https://learnmeabitcoin.com/beginners/guide/difficulty/}}
			\begin{itemize}
				\item New difficulty = Old difficulty $\times$ $\frac{\text{Target time}}{\text{Actual time}}$
				\item Blocks too fast? Difficulty $\uparrow$
				\item Blocks too slow? Difficulty $\downarrow$
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Example calculation:}
			\begin{itemize}
				\item 2016 blocks in 10 days (too fast!)
				      \begin{itemize}
					      \item Ratio = 14/10 = 1.4: difficulty +40\%
				      \end{itemize}
				\item 2016 blocks in 20 days (too slow!)
				      \begin{itemize}
					      \item Ratio = 14/20 = 0.7: difficulty $-$30\%
				      \end{itemize}
			\end{itemize}
			\begin{alertblock}{Safety limit, and a famous off-by-one}
				Clamped to at most 4$\times$ per period. Also, Bitcoin measures 2015 block intervals, not 2016: a bug now frozen into consensus.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The mining process: finding the golden ticket}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{What miners actually do:}
			\begin{enumerate}
				\item Collect pending transactions
				\item Create block with:
				      \begin{itemize}
					      \item Transactions
					      \item Hash of previous block
					      \item Timestamp
					      \item Nonce = 0
				      \end{itemize}
				\item Compute hash
				\item Check: enough zeros?
				\item If no: nonce++, try again
				\item If yes: Broadcast to network!
			\end{enumerate}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Why call it ``mining''?}
			\begin{itemize}
				\item Like prospecting: most attempts fail, a find is valuable
				\item The 4-byte nonce gives only $2^{32}$ tries; ASICs burn through them in milliseconds, then vary the coinbase or timestamp
			\end{itemize}
			\begin{exampleblock}{The reward}
				New bitcoins (3.125 BTC per block since April 2024, $\approx$\$200K at 2024 prices) plus the block's fees
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Why proof-of-work solves our problems}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Problem 1: Sybil attacks}
			\begin{itemize}
				\item Can't fake computational work
				\item 1000 identities at 1 hash/sec = 1 identity at 1000 hash/sec
				\item No advantage to splitting!
			\end{itemize}
			\textbf{Problem 2: Who decides ordering?}
			\begin{itemize}
				\item Whoever solves the puzzle first
				\item A lottery weighted by hashpower: 10\% of hashpower $\approx$ 10\% of blocks
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Problem 3: Double-spending}
			\begin{itemize}
				\item To rewrite history:
				      \begin{itemize}
					      \item Redo the work for that block and all after it
					      \item Faster than honest miners
				      \end{itemize}
				\item Success probability shrinks exponentially with depth
			\end{itemize}
			\begin{alertblock}{Security guarantee}
				Honest majority $\Rightarrow$ settled history is safe (probabilistically). Numbers shortly.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The economics: why anyone bothers to mine}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Mining costs:}
			\begin{itemize}
				\item ASICs: \$2,000--10,000 each, obsolete in a few years
				\item Electricity: the dominant cost
				\item Cooling, facilities, maintenance
			\end{itemize}
			\textbf{Mining revenue:}
			\begin{itemize}
				\item Block subsidy: 3.125 BTC (2024--2028)\footnote{\url{https://learnmeabitcoin.com/technical/mining/block-reward/}}
				\item Transaction fees
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Halving every 4 years: won't miners quit?}
			\begin{itemize}
				\item So far, BTC's price rose faster than the subsidy fell
				\item Fees are meant to take over
				\item Fewer miners $\Rightarrow$ lower difficulty $\Rightarrow$ cheaper mining
			\end{itemize}
			\begin{exampleblock}{Competition sets the security budget}
				Miners enter until cost $\approx$ reward. The reward is Bitcoin's security budget: what an attacker must match.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The environmental elephant in the room}
	\begin{center}
		\textbf{All this computation uses a lot of electricity}
	\end{center}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The scale:}
			\begin{itemize}
				\item Estimates: $\approx$100--180 TWh/year (2021--2024), depending on methodology
				\item Comparable to Argentina or the Netherlands
				\item Largest single sites: $\approx$700 MW, a small city
				\item Kazakhstan: $\approx$18\% of mining in late 2021; power shortages; crackdown in 2022
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The debate:}
			\begin{itemize}
				\item \textbf{Critics}: deliberately useless computation; very real energy
				\item \textbf{Supporters}: secures \$1T+ of value, uses stranded/renewable energy, gold mining is worse
			\end{itemize}
			\begin{alertblock}{For this course}
				The energy \emph{is} the security: what miners burn is what an attacker must outspend. Remember this for proof-of-stake.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Alternative PoW designs: can we do better?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The ASIC problem:}
			\begin{itemize}
				\item ASICs beat CPUs by orders of magnitude
				\item A few big farms dominate: so much for ``one CPU, one vote''
			\end{itemize}
			\textbf{Attempted fixes:}
			\begin{itemize}
				\item Memory-hard puzzles: scrypt (Litecoin), Ethash (Ethereum); cf.\ 1.6
				\item Random programs: RandomX (Monero); the only good ``ASIC'' is a CPU
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Example: Ethash}
			\begin{itemize}
				\item Random reads from a multi-GB dataset: memory bandwidth, not arithmetic, is the bottleneck
				\item GPUs stayed competitive; ASICs gained little
			\end{itemize}
			\begin{alertblock}{The trade-off}
				Broader participation, more complex puzzle. And ASIC resistance erodes anyway.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\subsection{Forks and Nakamoto Consensus}

\begin{frame}{Temporary forks: when two miners win simultaneously}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{What happens:}
			\begin{itemize}
				\item Miner A finds a block at height 100
				\item Miner B finds a different block at height 100
				\item Both valid!
				\item Half the network sees A first
				\item Half sees B first
				\item Temporary fork
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Resolution:}
			\begin{itemize}
				\item Both branches grow
				\item Next block extends one branch
				\item That branch becomes longer
				\item Everyone switches to the longer chain
				\item The losing block becomes ``orphaned'' (strictly: ``stale''); its miner gets nothing
			\end{itemize}
			\begin{alertblock}{Self-healing}
				The system automatically converges without any coordination!
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The longest-chain rule: follow the most work}
	\begin{center}
		\textbf{Simple rule: always extend the valid chain with the most cumulative proof-of-work}
	\end{center}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Why ``most work''?}
			\begin{itemize}
				\item Most work = most hashpower spent on it
				\item Most hashpower = the majority of miners
				\item Majority = honest, by assumption
				\item ``Longest'' is shorthand: Bitcoin compares total work, so a low-difficulty fork can't win on block count
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{What this buys us:}
			\begin{itemize}
				\item Consensus without voting, identities, or coordination
				\item The tie-breaker is a physical quantity (work), not an opinion
				\item A node that was offline can catch up and reach the same answer on its own
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{center}
		\textbf{This is Nakamoto consensus -- the heart of Bitcoin.}
	\end{center}
\end{frame}

\begin{frame}{The 51\% attack: the one big vulnerability}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{With $>$50\% of hashpower, an attacker:}
			\begin{itemize}
				\item Can mine a longer chain in private, then release it
				\item Can double-spend their \emph{own} transactions
				\item Can censor transactions
			\end{itemize}
			\textbf{But still cannot:}
			\begin{itemize}
				\item Spend others' coins (no private keys)
				\item Create coins: invalid blocks are rejected, whatever their work
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Why it hasn't happened to Bitcoin:}
			\begin{itemize}
				\item Matching the network's hashpower costs billions
				\item A visible attack would crash the price
				\item Selfish mining (Eyal--Sirer, 2013): trouble below 50\%
			\end{itemize}
			\begin{alertblock}{Economic, not cryptographic, security}
				Part 1 gave reductions; this is ``attacking costs more than it gains''. Small PoW coins have been 51\%-attacked (Ethereum Classic, 2019--2020).
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\subsection{Bitcoin Transactions and Ownership}

\begin{frame}{How Bitcoin defines ownership}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{No accounts, only keys:}
			\begin{itemize}
				\item Private key: Random 256-bit number
				      \begin{itemize}
					      \item Your secret
					      \item Proves ownership
					      \item Never share!
				      \end{itemize}
				\item Public key: derived from the private key
				      \begin{itemize}
					      \item Scalar multiplication on secp256k1 (1.8)
					      \item Signatures: ECDSA; Schnorr since 2021
				      \end{itemize}
				\item Address: a hash of the public key
				      \begin{itemize}
					      \item What you share
					      \item Like a bank account number
				      \end{itemize}
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The mailbox analogy:}
			\begin{itemize}
				\item Address = mailbox number
				      \begin{itemize}
					      \item Everyone can see it
					      \item Anyone can send to it
				      \end{itemize}
				\item Private key = mailbox key
				      \begin{itemize}
					      \item Only you have it
					      \item Only you can retrieve mail
				      \end{itemize}
			\end{itemize}
			\begin{alertblock}{Critical rule}
				Not your keys, not your coins!
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Electronic coins as chains of signatures}
	\begin{columns}[c]
		\begin{column}{0.42\textwidth}
			\textbf{To pay someone:}
			\begin{enumerate}
				\item Hash the previous transaction
				\item Add the recipient's public key
				\item Sign both with your private key
			\end{enumerate}
			\textbf{Anyone can verify every link.}
			\begin{alertblock}{One problem}
				Nothing stops you signing the same coin to two people. Hold that thought.
			\end{alertblock}
		\end{column}
		\begin{column}{0.58\textwidth}
			\imagewithcaption[0.82\textwidth]{bitcoin-transactions.png}{Bitcoin whitepaper, Figure 1}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The UTXO model: coins are bills, not balances}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Bitcoin has no account balances.}
			\begin{itemize}
				\item It tracks \textbf{unspent transaction outputs} (UTXOs)
				\item Like cash: a \$20 and a \$5 bill = two UTXOs worth \$25
				\item ``Your balance'' = the UTXOs your keys can unlock
			\end{itemize}
			\textbf{Paying \$15 with a \$20 bill:}
			\begin{itemize}
				\item Hand over the whole bill, get \$5 back as a new bill
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{You own a 5 BTC output and pay 2 BTC:}
			\begin{itemize}
				\item Input: the 5 BTC output (consumed)
				\item Output 1: 2 BTC to the recipient
				\item Output 2: 2.9 BTC change to you
				\item Fee: 0.1 BTC = inputs $-$ outputs, to the miner
			\end{itemize}
			\begin{exampleblock}{Why this model?}
				A double-spend is ``the same output consumed twice'': every node checks this against its UTXO set.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

			\begin{itemize}
				\item The first transaction in every block is special
				\item Called the ``coinbase transaction''

					      \item Bitcoin protocol term

\subsection{Solving the Double-Spend Problem}

\begin{frame}{The core problem: order without clocks}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Two spends of one coin: which came first?}
			\begin{itemize}
				\item No global clock; network delays vary
				\item An attacker can lie about timestamps
				\item Nodes may see the two spends in different orders
				\item A bank deciding the order is exactly what we wanted to remove
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Bitcoin's answer: the chain is the clock}
			\begin{itemize}
				\item ``Before'' means ``in an earlier block''
				\item First spend mined wins; every node applies the same rule
				\item Backdating = redoing all the work above
			\end{itemize}
			\begin{exampleblock}{Nakamoto's phrase}
				A ``distributed timestamp server'': agree on an order, make it expensive to change.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Preventing double-spend with proof-of-work}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Attacker tries to double-spend:}
			\begin{itemize}
				\item Sends transaction to merchant
				\item Merchant sees transaction in block
				\item Attacker secretly mines alternative chain
				      \begin{itemize}
					      \item Different transaction spending same coins
					      \item Tries to overtake honest chain
				      \end{itemize}
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Why it fails:}
			\begin{itemize}
				\item Honest miners keep extending main chain
				\item Attacker must mine faster than all honest miners combined
				\item Probability shrinks exponentially with every block
				\item After 6 blocks, a 10\% attacker wins $\approx$0.02\% of the time
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{alertblock}{Wait for confirmations}
		More blocks = more security. Six confirmations is the customary threshold.
	\end{alertblock}
\end{frame}

	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{How merchants handle this:}
			\begin{itemize}
				\item 0 confirmations: High risk
				      \begin{itemize}
					      \item Coffee shop: OK
					      \item Car dealership: No way
				      \end{itemize}
				\item 1 confirmation: Some risk
				      \begin{itemize}
					      \item $\approx$10 minutes wait
					      \item Acceptable for small amounts
				      \end{itemize}
				\item 6 confirmations: Standard
				      \begin{itemize}
					      \item $\approx$1 hour wait
					      \item Used by exchanges
				      \end{itemize}
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The math (a gambler's-ruin calculation):}\footnote{\url{https://bitcoin.org/bitcoin.pdf}, section 11}
			\begin{itemize}
				\item Attacker with 10\% hashpower:
				      \begin{itemize}
					      \item 1 block: $\approx$20\% success
					      \item 2 blocks: $\approx$5\% success
					      \item 6 blocks: $\approx$0.02\% success
				      \end{itemize}
				\item With 30\% hashpower:
				      \begin{itemize}
					      \item 6 blocks: $\approx$13\% success
				      \end{itemize}
			\end{itemize}
			\begin{exampleblock}{Security grows}
				Each confirmation exponentially decreases attack probability!
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\subsection{Merkle Trees}

\begin{frame}{Do I really need 600 GB to check that I got paid?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The chain is big:}
			\begin{itemize}
				\item A block holds 2000--3000 transactions, $\approx$1--2 MB
				\item A new block every 10 minutes since 2009
				\item Over 900,000 blocks by 2026
				\item Total: well over 600 GB, growing by $\approx$100 GB a year
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{What if you want to:}
			\begin{itemize}
				\item Run a Bitcoin wallet on your phone?
				\item Check that a specific payment to you was mined?
				\item Without downloading (and verifying) everything?
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{alertblock}{The question}
		Can you verify that a transaction is in a block without downloading the entire block?
	\end{alertblock}
\end{frame}

\begin{frame}{Merkle trees: one hash that stands for thousands}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The insight:}
			\begin{itemize}
				\item You don't need all the transactions
				\item You need a proof that \emph{one} transaction is included
				\item Hash functions can give us that
			\end{itemize}
			\textbf{What Bitcoin does:}
			\begin{itemize}
				\item Hash the transactions into a \textbf{binary tree of hashes}
				\item Put only the \textbf{root} (32 bytes) in the block header
				\item Prove any transaction with a handful of hashes
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{You have met these before:}
			\begin{itemize}
				\item 2.6: XMSS/SPHINCS+ hash one-time keys into one public key
				\item 2.1: Certificate Transparency logs
				\item 1.6: Merkle--Damg\aa rd, the \emph{other} Merkle construction
			\end{itemize}
			\begin{exampleblock}{Named after}
				Ralph Merkle (1979), also an independent inventor of public-key cryptography (``Merkle's puzzles'').
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Inside a Bitcoin block header}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The 80-byte header:}
			\begin{itemize}
				\item Version: 4 bytes
				\item Previous block hash: 32 bytes
				\item \textcolor{red}{\textbf{Merkle root: 32 bytes}}
				\item Timestamp: 4 bytes
				\item Difficulty target (``bits''): 4 bytes
				\item Nonce: 4 bytes
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The Merkle root:}
			\begin{itemize}
				\item One 32-byte hash for every transaction, in order
				\item Change, add, remove, or reorder one: the root changes
				\item PoW hashes the header, so the work commits to the transactions
			\end{itemize}
			\begin{alertblock}{Key property}
				The root is a \textbf{commitment} to the transaction list: binding by SHA-256's collision resistance.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{How to build a Merkle tree: step by step}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Start with transactions:}\footnote{\url{https://learnmeabitcoin.com/technical/block/merkle-root/}}
			\begin{itemize}
				\item Hash each transaction (Bitcoin: SHA-256 twice, at every level)
				\item These are the leaves
			\end{itemize}
			\textbf{Build upward:}
			\begin{enumerate}
				\item Pair adjacent hashes
				\item Concatenate them
				\item Hash the result
				\item This is the parent node
				\item Repeat until one hash left!
			\end{enumerate}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Example with 4 transactions:}
			\begin{itemize}
				\item Level 0 (leaves):
				      \begin{itemize}
					      \item H(Tx0), H(Tx1)
					      \item H(Tx2), H(Tx3)
				      \end{itemize}
				\item Level 1:
				      \begin{itemize}
					      \item H0-1 = hash(H(Tx0) $\|$ H(Tx1))
					      \item H2-3 = hash(H(Tx2) $\|$ H(Tx3))
				      \end{itemize}
				\item Level 2 (root):
				      \begin{itemize}
					      \item Root = hash(H0-1 $\|$ H2-3)
				      \end{itemize}
			\end{itemize}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The payoff: proofs of logarithmic size}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{To prove Tx2 is in the block:}
			\begin{itemize}
				\item You don't need the other 7 transactions
				\item Only the ``sibling path'': one hash per level
				      \begin{enumerate}
					      \item H(Tx3): sibling of the leaf
					      \item H0-1: sibling of the parent
					      \item H4-7: sibling of the grandparent
				      \end{enumerate}
				\item Plus Tx2 itself and the root from the header
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The math:}
			\begin{itemize}
				\item 8 transactions: 3 hashes
				\item 1,024 transactions: 10 hashes
				\item 1 million transactions: 20 hashes
				\item Proof length $= \lceil \log_2 n \rceil$ hashes of 32 bytes each
			\end{itemize}
			\begin{exampleblock}{In numbers}
				A 2,500-transaction block has 12 levels: a 384-byte proof (plus the transaction) instead of a $\approx$1 MB block, checked against an 80-byte header.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Step-by-step verification}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{What verifier has:}
			\begin{itemize}
				\item Transaction Tx2
				\item Merkle proof: [H(Tx3), H0-1, H4-7]
				\item Block header with root
			\end{itemize}
			\textbf{What verifier does:}
			\begin{enumerate}
				\item Hash Tx2 $\rightarrow$ H(Tx2)
				\item Combine with H(Tx3)
				\item Hash $\rightarrow$ H2-3
				\item Combine with H0-1
				\item Hash $\rightarrow$ H0-3
			\end{enumerate}
		\end{column}
		\begin{column}{0.5\textwidth}
			\begin{enumerate}
				\setcounter{enumi}{5}
				\item Combine with H4-7
				\item Hash $\rightarrow$ Computed Root
				\item Compare with header
			\end{enumerate}
			\begin{alertblock}{If they match}
				Tx2 is in the block. A different transaction with the same proof path would be a second preimage for SHA-256.
			\end{alertblock}
			\textbf{Data transferred:}\\
			Tx2 + 3 hashes = $\approx$400 bytes\\
			Instead of 1 MB!
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{SPV: simplified payment verification}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Full node:}
			\begin{itemize}
				\item Downloads every block
				\item Validates every transaction and signature since 2009
				\item Stores the full chain: 600+ GB
				\item Initial sync: hours to days
			\end{itemize}
			\textbf{Not practical on a phone.}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{SPV client (Nakamoto, section 8):}
			\begin{itemize}
				\item Downloads only block headers
				\item 80 bytes $\times$ 900,000+ blocks $\approx$ 72 MB
				\item Checks the proof-of-work on each header
				\item Asks full nodes for Merkle proofs of the transactions it cares about
			\end{itemize}
			\begin{exampleblock}{$\approx$8000$\times$ smaller}
				This is why a Bitcoin wallet can run on a phone.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{How SPV wallets work, and what they trust}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Setup:}
			\begin{enumerate}
				\item Download all block headers
				\item Check PoW and links; keep the heaviest chain
			\end{enumerate}
			\textbf{When a payment arrives:}
			\begin{enumerate}
				\item Peer: ``you were paid in block $N$''
				\item Wallet: ``prove it''
				\item Peer (a full node) sends the sibling path
				\item Wallet hashes up to the root, compares with header $N$
			\end{enumerate}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{What the wallet trusts:}
			\begin{itemize}
				\item \textbf{Verified}: the transaction is in a block with real work behind it
				\item \textbf{Not verified}: that it is \emph{valid}. A bad miner can include an invalid transaction with a perfect proof
				\item So: wait for confirmations, talk to several peers, rely on the honest majority to reject bad blocks
				\item Full nodes verify; SPV clients verify inclusion and trust the hashpower
			\end{itemize}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Handling odd transaction counts (and a real bug)}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The problem:}
			\begin{itemize}
				\item A binary tree wants pairs. What if there are 5?
			\end{itemize}
			\textbf{Bitcoin's fix:}
			\begin{itemize}
				\item Duplicate the last hash at any odd level
				\item Leaves: H(Tx0), \ldots, H(Tx4), \textcolor{red}{H(Tx4)}
				\item Only the \emph{hash} is repeated, not the transaction
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The catch (CVE-2012-2459):}
			\begin{itemize}
				\item $[A,B,C]$ and $[A,B,C,C]$: same root
				\item Send a peer the duplicated version: same header, but an invalid block
				\item The peer blacklists the hash, then rejects the real block too
				\item Fixed in 2012
			\end{itemize}
			\begin{alertblock}{Lesson}
				Collisions for free. Hash unambiguous encodings.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Beyond Bitcoin: Merkle trees everywhere}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Other blockchains:}
			\begin{itemize}
				\item Ethereum: several Merkle(-Patricia) trees per block: transactions, receipts, account state
				\item Light clients get balance proofs against the state root
			\end{itemize}
			\textbf{Outside cryptocurrency:}
			\begin{itemize}
				\item Git (next slide), IPFS, BitTorrent
				\item Certificate Transparency (2.1)
				\item Hash-based signatures (2.6)
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Variants:}
			\begin{itemize}
				\item Sparse Merkle trees: key--value maps with proofs of \emph{absence}
				\item Merkle-sum trees: nodes also sum their children (proof-of-reserves)
				\item Verkle trees: vector commitments, shorter proofs
			\end{itemize}
			\begin{exampleblock}{The general name}
				\textbf{Authenticated data structures}: a short digest lets you verify answers about data held by someone you don't trust.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Example: Git is a blockchain!}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Git commits are blocks:}
			\begin{itemize}
				\item A commit hashes: the file tree (itself a Merkle tree), a timestamp, the parent commit's hash, optionally a signature
				\item A chain back to the initial commit
				\item Change one commit $\rightarrow$ every later hash changes
				\item Still SHA-1 by default (1.6: SHAttered!)
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Key differences:}
			\begin{itemize}
				\item Git: no proof-of-work; anyone with push access can rewrite history (\texttt{git push -{}-force})
				\item Git: you trust whoever hosts the repository
				\item Bitcoin: rewriting costs work; the rule for who appends is the whole point
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{exampleblock}{Same primitive, different consensus}
		A hash chain is \textbf{tamper-evident}. A blockchain adds a rule for who may append, making rewriting \textbf{tamper-expensive}.
	\end{exampleblock}
\end{frame}

\begin{frame}{Putting it all together: the full picture}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Transactions:}
			\begin{itemize}
				\item Signatures (ECDSA or Schnorr on secp256k1) prove who may spend
				\item Spent outputs are consumed; new outputs are created
			\end{itemize}
			\textbf{Blocks:}
			\begin{itemize}
				\item Bundle transactions under one Merkle root
				\item 80-byte header: previous hash, Merkle root, timestamp, target, nonce
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Mining:}
			\begin{itemize}
				\item Double-SHA-256 lottery; difficulty retargets every 2016 blocks
				\item Block subsidy plus fees pay for the security
			\end{itemize}
			\textbf{Consensus:}
			\begin{itemize}
				\item Follow the chain with the most work
				\item Double-spends lose the race; confirmations make winning it exponentially unlikely
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{center}
		\textbf{Result: a public ledger nobody controls, built from hashes, signatures, and a puzzle.}
	\end{center}
\end{frame}

\begin{frame}{Discussion time}
	\begin{columns}[c]
		\begin{column}{0.68\textwidth}
			\begin{enumerate}
				\item \textbf{Is ``economic security'' security?}
				      \begin{itemize}
					      \item Part 1 gave us reductions. Bitcoin's argument is ``attacking costs more than it pays''. What assumptions does that hide?
				      \end{itemize}
				\item \textbf{What is an SPV wallet actually trusting?}
				      \begin{itemize}
					      \item List every party and assumption between ``I see a Merkle proof'' and ``I was paid''.

\section{Ethereum and Smart Contracts}

\begin{frame}{Bitcoin does one thing. What if the ledger could run programs?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Bitcoin, deliberately:}
			\begin{itemize}
				\item Moves coins under simple conditions: signatures, timelocks, multisig
				\item No loops in its scripting language: every script terminates
				\item One job: be money
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Ethereum (whitepaper 2013, live July 2015):}
			\begin{itemize}
				\item Vitalik Buterin: a blockchain that stores \emph{code}, not just balances
				\item Every node runs the code and agrees on the result: a ``world computer''
				\item The EVM is Turing-complete; anyone can deploy
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{alertblock}{Result}
		``Smart contracts'': programs enforced by consensus rather than by a court.
	\end{alertblock}
\end{frame}

\begin{frame}{From Bitcoin to Ethereum}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Bitcoin:}
			\begin{itemize}
				\item UTXO model (like cash)
				\item Limited scripting
				\item Tracks coin ownership
				\item Simple state transitions
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Ethereum:}
			\begin{itemize}
				\item Account model (like bank accounts)
				\item Full programming
				\item Tracks balances + code + data
				\item Complex state machine
			\end{itemize}
		\end{column}
	\end{columns}
	\vspace{1em}
	\begin{center}
		\textbf{Every transaction can trigger arbitrary code execution}

\subsection{Smart Contracts}

\begin{frame}{What are smart contracts?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Nick Szabo's vending machine (1990s):}
			\begin{itemize}
				\item Insert \$1.50 $\rightarrow$ get soda
				\item Rules built into machine
				\item No human intermediary
				\item Can't cheat the machine
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Smart contracts:}
			\begin{itemize}
				\item Code on blockchain
				\item Rules in the code
				\item Executes automatically
				\item Runs exactly as written, whether or not that is what anyone intended
			\end{itemize}
		\end{column}
	\end{columns}
	\begin{exampleblock}{Four key properties}
		Immutable \textbullet{} Deterministic \textbullet{} Autonomous \textbullet{} Transparent

\begin{frame}{The gas mechanism: paying for computation}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Problem:}
			\begin{itemize}
				\item What stops infinite loops?
				\item What prevents spam?
				\item How to price CPU time?
			\end{itemize}
			\textbf{Solution: Gas}
			\begin{itemize}
				\item Every operation costs gas
				\item Storage most expensive
				\item Simple math cheap
				\item User pays for execution
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Gas prices:}
			\begin{itemize}
				\item ADD: 3 gas
				\item MUL: 5 gas
				\item SSTORE (new storage slot): 20,000 gas
			\end{itemize}
			\textbf{How it works:}
			\begin{itemize}
				\item Fee = gas used $\times$ your gas price
				\item Out of gas? Reverts (and you still pay)
			\end{itemize}
			\begin{exampleblock}{Halting problem, sidestepped}
				Every program halts: it runs out of money.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The fee market since EIP-1559 (August 2021)}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Gas is a unit, not a coin:}
			\begin{itemize}
				\item Like kilowatt-hours: you pay in ETH per unit of gas
			\end{itemize}
			\textbf{The price has two parts:}
			\begin{itemize}
				\item \textbf{Base fee}: protocol-set, \emph{burned}; moves up to 12.5\% per block toward half-full blocks. Difficulty adjustment, for fees
				\item \textbf{Priority fee} (tip): yours, paid to the validator
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Worked example: a plain ETH transfer}
			\begin{itemize}
				\item Gas used: 21,000
				\item Base fee 30 gwei, tip 2 gwei (1 gwei $= 10^{-9}$ ETH)
				\item Cost: $(30 + 2) \times 21{,}000 = 672{,}000$ gwei $= 0.000672$ ETH
				\item 630,000 gwei burned, 42,000 to the validator
			\end{itemize}
			\begin{exampleblock}{Market dynamics}
				High demand $\rightarrow$ base fee climbs. In a hurry $\rightarrow$ raise your tip.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}[fragile]{A real example: a simple token}
	\scriptsize
	\begin{verbatim}
pragma solidity ^0.8.0;

contract SimpleToken {
  mapping(address => uint256) public balances;

  constructor(uint256 initialSupply) {
    balances[msg.sender] = initialSupply;
  }
  function transfer(address to, uint256 amount) public returns (bool) {
    require(balances[msg.sender] >= amount, "Insufficient balance");
    balances[msg.sender] -= amount;
    balances[to] += amount;
    return true;
  }
}
\end{verbatim}
	\textbf{Key concepts:} \texttt{msg.sender} (who called?), \texttt{mapping} (key-value storage), \texttt{require} (abort if false). Add \texttt{approve}/\texttt{transferFrom}: an \textbf{ERC-20} token. Before Solidity 0.8, \texttt{+=} silently overflowed.
\end{frame}

			\end{exampleblock}

\end{frame}

\begin{frame}[fragile]{The DAO hack: when code goes wrong}
	\begin{columns}[c]
		\begin{column}{0.45\textwidth}
			\textbf{Spring 2016:}
			\begin{itemize}
				\item ``The DAO'' raises $\approx$\$150M in ETH, the largest crowdfund to date
				\item A venture fund run entirely by its contract
			\end{itemize}
			\textbf{June 17, 2016:}
			\begin{itemize}
				\item An attacker drains 3.6M ETH ($\approx$\$50M) via \textbf{reentrancy}
			\end{itemize}
			\begin{alertblock}{The bug in one sentence}
				It sends the money \emph{before} updating the balance.
			\end{alertblock}
		\end{column}
		\begin{column}{0.55\textwidth}
			\scriptsize
			\begin{verbatim}
function withdraw() public {   // simplified
  uint256 amount = balances[msg.sender];
  // sending ETH to a contract RUNS ITS CODE...
  (bool ok, ) = msg.sender.call{value: amount}("");
  require(ok);
  // ...which calls withdraw() again before
  // we ever get here:
  balances[msg.sender] = 0;
}
\end{verbatim}
			\normalsize
			\textbf{Fix}: zero the balance before the call (checks, effects, interactions), or a reentrancy lock.
		\end{column}
	\end{columns}
\end{frame}

\subsection{Proof-of-Stake: The Merge}

\begin{frame}{The energy problem}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Ethereum's PoW:}
			\begin{itemize}
				\item Like Bitcoin mining (Ethash, from the ASIC-resistance slide)
				\item $\approx$78 TWh/year before The Merge
				\item More than Austria!
			\end{itemize}
			\textbf{The question:}
			\begin{itemize}
				\item Can we secure the network...
				\item Without burning energy?
				\item Still stay decentralized?
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Proof-of-Stake idea:}
			\begin{itemize}
				\item Replace miners with validators
				\item Stake ETH as collateral
				\item Get randomly selected
				\item Misbehave? Lose your stake!
			\end{itemize}
			\begin{exampleblock}{Core insight}
				Economic security instead of energy security
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{The Merge: 15 September 2022}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{What happened:}
			\begin{itemize}
				\item A proof-of-stake chain (the Beacon Chain) had run alongside since December 2020: real stake, no transactions
				\item At a preset total difficulty, mining stopped and the old chain became the Beacon Chain's payload
				\item No downtime; balances, contracts, history unchanged
				\item Changing the engines in flight, with $\approx$\$200B on board
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Results:}
			\begin{itemize}
				\item $\approx$99.95\% less energy
				\item By 2024: $\approx$1M validators, 30M+ ETH staked (a quarter of all ETH)
				\item Finality after two epochs ($\approx$13 min): reverting it would burn at least a third of all stake
			\end{itemize}
			\begin{exampleblock}{Fun fact}
				GPU mining rigs worth billions became useless overnight. Some moved to Ethereum Classic.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{How proof-of-stake works: carrots and sticks}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Become a validator:}
			\begin{itemize}
				\item Deposit 32 ETH
				\item Stay online; sign what the protocol asks
				\item Each 12 s slot: a random validator proposes a block, committees \textbf{attest}
			\end{itemize}
			\textbf{Carrots:}
			\begin{itemize}
				\item $\approx$3--5\% a year for timely, correct attestations and proposals
				\item Proposers also collect tips
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Sticks:}
			\begin{itemize}
				\item Offline: lose about what you'd have earned (far worse if finality stalls: the ``inactivity leak'')
				\item \textbf{Slashing}: sign two conflicting messages, lose 1+ ETH, get ejected
				\item Slashed ETH is burned
			\end{itemize}
			\begin{alertblock}{Skin in the game}
				Sybils fail as in PoW: 1000 validators with 32 ETH cost the same as one with 32,000 ETH.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

% Roles and timing: https://ethereum.org/developers/docs/consensus-mechanisms/pos/
\begin{frame}{A slot: one proposal, many independent checks}

\begin{frame}{How is dishonesty detected?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{The watchers:}
			\begin{itemize}
				\item Every block and attestation is signed and public
				\item Anyone can look for contradictions
			\end{itemize}
			\textbf{Slashable offenses:}
			\begin{itemize}
				\item \textbf{Double proposal}: two blocks for one slot
				\item \textbf{Double vote}: two attestations for one target
				\item \textbf{Surround vote}: contradicting your own earlier finality vote
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Detection mechanism:}
			\begin{enumerate}
				\item A validator signs two conflicting messages
				\item Anyone submits both on-chain
				\item The protocol checks the signatures and slashes
				\item The whistleblower gets a small reward
			\end{enumerate}
			\begin{exampleblock}{Non-repudiation, weaponized}
				Its own two signatures are on the chain: no denying it.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Critiques of proof-of-stake}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Nothing at stake:}
			\begin{itemize}
				\item PoW: mining two forks splits your hashpower. PoS: signing both is free
				\item So why not vote for every fork?
				\item Answer: slashing
			\end{itemize}
			\textbf{Long-range attacks:}
			\begin{itemize}
				\item Exited validators can rewrite old history with old keys, for free
				\item Answer: new nodes start from a recent checkpoint (``weak subjectivity''); PoW never needed that
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Concentration:}
			\begin{itemize}
				\item Rewards accrue to existing holders
				\item 32 ETH is a high bar, so most stake via pools; Lido alone held $\approx$30\% in 2023--2024
				\item Pools reintroduce the intermediaries we set out to remove
			\end{itemize}
			\begin{alertblock}{The debate}
				PoW is anchored in physics; PoS in the token's own value. Circular, or just honest?
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\subsection{Scaling: Layer 2s}

\begin{frame}{The blockchain trilemma}
	\begin{center}
		\textbf{Pick any two:}
	\end{center}
	\begin{columns}[c]
		\begin{column}{0.33\textwidth}
			\centering
			\textbf{Decentralization}\\
			Many validators
		\end{column}
		\begin{column}{0.33\textwidth}
			\centering
			\textbf{Security}\\
			Attack-resistant
		\end{column}
		\begin{column}{0.33\textwidth}
			\centering
			\textbf{Scalability}\\
			High throughput
		\end{column}
	\end{columns}
	\vspace{1em}
	\begin{center}
		\textbf{The problem:}\\
		Ethereum: $\approx$15--30 transactions per second\\
		Visa: $\approx$2,000 on an average day, 65,000 claimed capacity\\
		Gap: two to three orders of magnitude
	\end{center}
	\begin{alertblock}{Why so slow?}
		Every node processes every transaction. Can't just use bigger servers!
	\end{alertblock}
\end{frame}

\begin{frame}{Layer 2: don't make every node do everything}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Key insight:}
			\begin{itemize}
				\item Execute elsewhere; put only the \emph{result}, plus enough data to check it, on Ethereum
				\item A ``rollup'' batches thousands of transactions off-chain and posts a summary plus a new state root to an L1 contract
			\end{itemize}
			\textbf{L1 (Ethereum):}
			\begin{itemize}
				\item Security, final settlement, and data availability
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{L2 (rollups):}
			\begin{itemize}
				\item Execute transactions cheaply and quickly
				\item Store their state as a Merkle root on L1
				\item Anyone can exit to L1 with a Merkle proof of their balance
			\end{itemize}
			\begin{exampleblock}{The question that defines an L2}
				How does the L1 contract know the posted root is correct? Two answers next.
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Two answers: optimistic and ZK rollups}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Optimistic rollups:}
			\begin{itemize}
				\item Post the root and \emph{assume} it is correct
				\item Within $\approx$7 days, anyone may submit a \textbf{fraud proof}
				\item If fraud: root discarded, poster loses a bond
				\item Cost: slow withdrawals
			\end{itemize}
			\textbf{Examples:} Arbitrum, Optimism, Base
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{ZK rollups:}
			\begin{itemize}
				\item Post the root with a \textbf{validity proof} of correct execution
				\item L1 verifies it in milliseconds
				\item Cost: proving is expensive and complex
			\end{itemize}
			\textbf{Examples:} zkSync, Starknet
			\begin{alertblock}{A naming quirk}
				They need succinctness, not zero-knowledge; the name stuck. Details in 2.8.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{Where this leaves us}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Honest caveats about L2s:}
			\begin{itemize}
				\item Most rollups today are run by a single ``sequencer'' that can delay or reorder your transaction
				\item Moving assets between chains goes through bridges, which have suffered the biggest hacks in the industry (Ronin, \$620M, and Wormhole, \$320M, both in 2022)
				\item Many rollups shipped with training wheels: a multisig that can override the contracts
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{The direction of travel:}
			\begin{itemize}
				\item Ethereum as the settlement and data layer; execution moves to L2s
				\item Which means the cryptography in 2.8 is no longer academic: validity proofs are settling real money today
			\end{itemize}
			\begin{exampleblock}{Look ahead}
				Next lecture: how do you prove that a computation was done correctly, with a proof far shorter than the computation?
			\end{exampleblock}
		\end{column}
	\end{columns}
\end{frame}

\begin{frame}{What was actually cryptographic today?}
	\begin{columns}[c]
		\begin{column}{0.5\textwidth}
			\textbf{Cryptography doing the work:}
			\begin{itemize}
				\item \textbf{Hash functions} (1.6): the PoW lottery, the hash chain, Merkle trees
				\item \textbf{Signatures} (1.7, 1.8): who may spend; slashing evidence
				\item \textbf{Commitments}: a Merkle root, 32 bytes for thousands of transactions
				\item \textbf{Succinct proofs} (2.8): validity rollups
			\end{itemize}
		\end{column}
		\begin{column}{0.5\textwidth}
			\textbf{Not cryptography, but load-bearing:}
			\begin{itemize}
				\item Honest-majority assumptions
				\item ``Attacking costs more than it pays'': economics
				\item Social consensus: the DAO fork showed the code loses when enough people disagree with it
			\end{itemize}
			\begin{alertblock}{Takeaway}
				A blockchain = hash chain + append rule. Cryptography makes cheating \emph{detectable}; consensus makes it \emph{expensive}.
			\end{alertblock}
		\end{column}
	\end{columns}
\end{frame}
